**Catalog facts:** migration `0024_pricing_catalog.py` seeds precisely nine OCI BRL rows
(6 compute, 1 Windows, 2 volume), source `IMPORTED_OCI_CALCULATOR`, effective 2026-10-01.
The `PricingCatalogItem` identity is `(provider, service, sku, unit, effective_from)`;
there is no separate region field. `PricingResolver` resolves one enabled,
non-overlapping, effective-dated row, with optional expected currency, and raises for
missing, ambiguous or wrong-currency matches. OCI computation uses **744 hours/month**,
`Decimal` and `ROUND_HALF_UP` to cents. Catalog administration and price audit are
already implemented for OCI under Settings; the provider-neutral admin service can be
reused for approved new rows, subject to authorized administration.

commercial contract was accessed. Therefore the seeded matrix is confirmed from
migrations, not a claim that every deployed installation still has only those rows.
Current effective prices may differ due to administrative versions.

### Critical OCI commercial constraints

Oracle's current Base Database Service documentation states that VM.Standard.x86
shapes, EE-EP edition, and **OCPU-metered Base Database Service SKUs retired from new
provisioning/renewals effective 31 July 2026**; existing deployments may continue.
**New DB System simulations must not silently offer historical OCPU combinations.**
Model new ECPU-based VM.BaseDB.x86 where supported, and treat historical OCPU pricing
as a separately qualified read-only legacy scenario, not automatically available.
Further qualification by service, region, tenancy, shape, database edition and license
model is necessary before enabling options.

Official Oracle reference:
https://docs.oracle.com/en/cloud/paas/base-database/guide/about.html

Oracle documents two license choices:
`license_included` (service plus Oracle Database license) and `byol` (customer
provides eligible software licenses). Do not assume the same SKU, term or rate for
both; the `license_included` price may already contain license value and must not
be supplemented with a duplicate license component.

https://docs.oracle.com/en/cloud/paas/base-database/guide/dbs-create-new.html

OCI Compute E3/E4/E5 shapes appear in Oracle's shape/resize documentation, but
documentation support does **not** guarantee that any shape is currently available for
new provisioning in every tenancy, region and compartment. Future option discovery
must apply an eligibility policy and avoid presenting discontinued combinations as
unconditionally available.

## 2. Architecture and ownership

- **Contracts:** `backend/app/schemas/calculator.py` defines Pydantic input/output
  models for AWS EC2, AWS RDS, OCI Compute VM and OCI DB System, quantity, region,
  temporal period, manual AWS financial terms and component-level provenance.
- **Catalog adapter:** `backend/app/services/calculator_foundation.py` reuses
  `PricingResolver` and `PricingIdentity` without inserting any catalog entries.
  `CalculatorCatalogAdapter.resolve` distinguishes missing SKU from a known
  identity with no effective price. Incompatible currency or overlapping prices
  become a pricing configuration error. Every non-priced lookup returns **None**
  for its unit price; it must never return an invented `0`.
- **OCI mapping:** `oci_compute_catalog_identities` uses the exact approved
  `OCI_COMPUTE_PRICE_KEYS`, `resolve_compute_price_family` and volume/Windows
  constants. It never maps a Compute shape to a DB System SKU.
- **Financial terms:** `apply_aws_financial_terms` is a pure adjustment primitive
  that discounts eligible USD components, optionally converts the USD net to BRL
  with user-entered FX, then adds entered tax. It does **not** select SKUs, meter
  durations or implement the future complete calculator.
- **Compatibility:** no changes to migrations, existing price tables, API routes,
  Billing, Opportunities, RDS Reservations, worker or historic records. No account
  requirement, cloud provider SDK call, or provisioning permission is introduced.

The Pydantic objects are **internal planned API contracts**, not yet an advertised
HTTP endpoint. Task 27.2 should introduce an application service, and a later task
will expose authenticated, authorized routes. The frontend must only render values
from the backend, not replicate financial formulas.

## 3. Contract of request and response

Request: `provider`, `region`, service-tagged `resource_configuration`,
`quantity` (integer >=1), `period`, optional `pricing_reference_date`,
optional AWS-only `aws_financial`.

Supported period modes: `monthly`, `hours`, `days`, `weeks`,
`custom` with aware `start_at` and `end_at` (exclusive end). Duration quantities
may be fractional. Input validity is enforced before any pricing lookup. Missing
service-specific selectors remain nullable in foundation contracts so the later
resolution layer can return `missing_configuration` with precise missing fields,
rather than a bogus zero-cost estimate. The request never requires a cloud account.

Response: `provider`, `service`, `region`, `resource_configuration`,
`quantity`, `period`, `pricing_components`, `pricing_source`,
`pricing_reference_date`, `pricing_currency`, monthly and period original/net/
final totals, AWS adjustment fields, `final_currency`, `pricing_status`,
`missing_pricing_components`, `warnings`. All financial totals are nullable
until priced. Non-`priced` statuses must never expose monthly or period final totals,
including fake zeroes. The response service must match its tagged resource configuration
and the selected provider. Each priced component retains identity, unit rate, usage quantities,
currency, source, effective dates and catalog-item ID. No UI-facing text is embedded
in status codes.

Statuses:

| Code | Meaning |
| --- | --- |
| `priced` | All required components priced; monthly and period totals present |
| `partially_priced` | Some but not all required components available; don't advertise partial subtotal as the full estimate |
| `sku_missing` | No catalog identity exists |
| `price_not_effective` | Identity exists, but no enabled price applies at reference date (future, expired or inactive) |
| `unsupported_configuration` | Unsupported SKU/shape/region or non-offered commercial combination |
| `missing_configuration` | Required selectors/quantities not provided |
| `invalid_combination` | Inputs contradict service or licensing constraints |
| `pricing_configuration_error` | Catalog ambiguity, currency mismatch or other invalid price configuration |

## 4. Financial contract

**AWS:** catalog base currency USD, discount default 0% (0–100%) only on
components explicitly marked eligible. No catalog mutation.

```text
original_usd = eligible_usd + noneligible_usd
discount_usd = eligible_usd * (discount_percent / 100)
net_usd = original_usd - discount_usd
if conversion_enabled:
    converted_brl = net_usd * manually_entered_usd_brl_rate
    tax_brl = converted_brl * (tax_percent / 100)
    final_brl = converted_brl + tax_brl
else:
    final_usd = net_usd
```

FX flag off by default; FX rate is required and >0 only if enabled;
tax defaults to 13% and is nonnegative, applied only when converting. The
financial primitive preserves full `Decimal` intermediate precision, rounds
reported monetary amounts once to two decimal places using `ROUND_HALF_UP`.
For a multi-component estimate, calculate raw component contributions first
and round final aggregates to avoid cumulative rounding drift. Component
discount eligibility must be based on the real AWS contract; do not assume
tax/discount eligibility for storage, licenses or marketplace items.

**OCI:** selected catalog values are already final commercial **BRL**, with
discount and tax incorporated. Do not offer extra discount/FX/tax for OCI or
apply these rules to historical OCI opportunities. When provided, each original, net
and final OCI amount must match: there is no second financial adjustment. Keep provenance for each SKU
and include storage and Windows exactly once when applicable.

No exchange-rate API or automatic exchange-rate refresh is planned for this phase.

## 5. Time and metering contract for Task 27.2

- Monthly is a **reference cost**, not a promise that all actual calendar months
  have the same hours or AWS billable seconds.
- Hours/days/weeks and custom date ranges must be converted to a precise elapsed
  duration, preferably using UTC-aware instants. Do not count a date range as
  an integer number of days when it includes partial days.
- `OCPU_HOUR`, `GB_RAM_HOUR`, `ECPU_HOUR`, `INSTANCE_HOUR`,
  and actual per-second/minute dimensions must each have explicit billing
  precision and minimum charge rules verified for their selected provider/SKU.
- `GB_MONTH`, `VPU_GB_MONTH`, provisioned storage, licensing and minimums
  require their **own** time basis and proration; never divide every component
  by an arbitrary fixed number of hours.
- For existing OCI Compute estimates, preserve `OCI_MONTHLY_HOURS=744`.
  Other OCI products and AWS monthly estimates need independently documented
  conversion conventions. AWS Cost Explorer observed costs are not a time-rate
  catalogue.
- Price changes inside long custom periods require a defined policy
  (snapshot at `pricing_reference_date` for a simulation vs splitting intervals
  at catalog effective boundaries); the response must identify the policy.
- Multiply by resource count and duration **before** rounding totals. For
  insufficient data, return a non-priced status and absent totals.
- Task 27.2 must separately validate zero-cost legitimately free SKUs vs missing
  prices; the mere absence of a SKU is never free usage.
