## 1. Visão geral e biblioteca

A infraestrutura oficial de idioma utiliza **next-intl 4.3.5** (App Router, Next.js 15, React 19, TypeScript) e o parser ICU @formatjs/icu-messageformat-parser 2.11.2 para validação em build/CI. A aplicação não utiliza rotas por idioma, middleware de locale ou bibliotecas próprias de interpolação. A auditoria 25.1 recomendou este desenho.

Os idiomas oficiais são pt-BR (padrão) e en-US; a preferência persistida é um cookie de apresentação, não um atributo de conta e não um indicador de moeda. A infraestrutura só traduz mensagens que optarem por chaves; **as telas existentes ainda podem conter português e inglês** até as Tasks 25.3–25.7.

## 2. Arquitetura e arquivos

- frontend/i18n/locales.mjs + locales.d.mts: allowlist, tipos, resolução determinística, leitura segura de header e opções de cookie.
- frontend/i18n/server.ts: resolução do locale por request, via cookies assíncronos do Next 15.
- frontend/i18n/request.ts: getRequestConfig do next-intl, sem locale routing.
- frontend/i18n/catalog.ts: catálogos em memória e merge profundo com pt-BR como fallback apenas de mensagens.
- frontend/i18n/messages/{pt-BR,en-US}.json: chaves semânticas e valores reais de common, shell e errors.
- frontend/i18n/global.d.ts: tipagem das chaves e do locale via AppConfig oficial do next-intl.
- frontend/i18n/fallback.ts: texto localizado e estável quando a chave não existir em nenhum catálogo.
- frontend/components/locale-provider.tsx: wrapper cliente mínimo do NextIntlClientProvider, com tratamento de erro consistente.
- frontend/i18n/actions.ts: Server Action segura que valida e persiste a preferência.
- frontend/i18n/use-locale-preference.ts: hook cliente para a futura UI; atualiza cookie e RSC sem mudar URL.
- frontend/next.config.mjs: plugin oficial apontando para i18n/request.ts.
- frontend/app/layout.tsx: getLocale, getMessages, HTML lang e LocaleProvider acima de ThemeProvider.
- frontend/scripts/check-i18n.mjs e frontend/tests/aven-i18n-foundation.test.mjs: checagem de estrutura, duplicação, ICU e casos principais.

A estrutura segue a convenção de nomes da Task 25.1: namespaces em minúsculas, caminhos semânticos em inglês com segmentos camelCase, mensagens em ICU e parâmetros nomeados. Os namespaces adicionais (auth, dashboard, billing, flow, inventory, opportunities, reservations, collections, scans, settings e accessibility) serão criados quando tiverem mensagens reais nas próximas tasks, evitando placeholders fictícios.

## 3. Consumo de traduções

Server Component (não requer use client):

    import {getTranslations} from "next-intl/server";
    export default async function Example() {
      const t = await getTranslations("common");
      return <span>{t("actions.save")}</span>;
    }

Client Component:

    "use client";
    import {useTranslations, useLocale} from "next-intl";
    export function Example() {
      const t = useTranslations("common");
      const locale = useLocale();
      return <span lang={locale}>{t("results.count", {count: 3})}</span>;
    }

Para metadados dinâmicos, usar getTranslations/getLocale no servidor, sem traduzir o nome próprio Aven. O tipo de mensagens deriva diretamente do JSON pt-BR, sem lista de chaves duplicada manualmente.

## 4. Resolução, cookie e segurança

Ordem: preferência explícita válida (contrato de resolução); preferência persistida válida; fallback pt-BR. O Root Layout não detecta o idioma do navegador nem depende de localStorage. Cookie: **aven.locale**, Path=/, SameSite=Lax, Max-Age=31536000 s (365 dias), HttpOnly, Secure em NODE_ENV=production. Valores aceitos apenas pt-BR e en-US; valores vazios, desconhecidos ou corrompidos retornam pt-BR. Dados sensíveis e valores de negócio não são gravados.

A escrita ocorre apenas pelo Server Action updateLocalePreference(requested), com validação por allowlist. Seu resultado informa ok/locale; requisições inválidas não gravam cookie. Uma falha de escrita retorna erro ao chamador em vez de alterar somente a UI. O estado de autenticação e os cookies próprios de sessão permanecem intocados.

Em ambiente de desenvolvimento HTTPS reverso (NODE_ENV diferente de production), a política Secure pode requerer ajuste de deployment, mas nenhum caminho arbitrário do cookie é usado em import ou arquivo.

## 5. SSR, hidratação e cache

O Root Layout é assíncrono: getLocale e getMessages consultam o mesmo getRequestConfig por request. O HTML inicial já recebe lang igual ao locale das mensagens; LocaleProvider recebe exatamente esse snapshot (locale e messages). Não há leitura de preferências de idioma em useEffect, nem bootstrap cliente que provoque flash de idioma. getRequestConfig resolve cookies de forma dinâmica, portanto as renderizações dependentes do locale não devem ser tratadas como HTML estático compartilhado. Respostas de CDN/proxy não devem cachear HTML autenticado ou RSC sem considerar cookie/usuário. O cache interno por request do next-intl não compartilha locale mutável entre usuários.

A propriedade suppressHydrationWarning do HTML permanece **exclusivamente** por compatibilidade com o bootstrap preexistente de tema/sidebar; não é mecanismo de correção de divergência de idioma. Não foram adicionados localePrefix, middleware, pasta [locale] ou redirects.

## 6. Fallback e integridade

Locale ausente ou inválido → pt-BR. Chave ausente em en-US mas existente em pt-BR → mensagem pt-BR (merge das folhas). Chave ausente em ambos → "Tradução indisponível" ou "Translation unavailable", com diagnóstico no console em desenvolvimento; nunca mostrar uma stack trace ou a chave crua ao usuário. A auditoria de catálogos deve falhar em CI se houver divergência, mesmo que o fallback runtime exista.

O comando npm run lint:i18n compara a paridade de chaves em ambos os JSON, rejeita duplicações de chave, strings vazias, identificadores não semânticos, ICU malformado, casos ICU sem other e incompatibilidade entre nomes e tipos de parâmetros. A suíte cobre interpolação e pluralização efetivas via createTranslator.

## 7. Integração com tema e futuras mudanças

A nova árvore é LocaleProvider → ThemeProvider → AvenAmbientBackground → ToastProvider → AppShell. Nenhum valor de tema, token, preferência visual, cookie de sessão, localStorage de tema ou localStorage da sidebar foi alterado. O idioma é uma dimensão independente: os três modos de tema são permitidos em qualquer locale.

Na Task 25.3, colocar o seletor ao lado de ThemeControl (incluindo acessibilidade e responsive), chamar:

    const {locale, changeLocale, isPending} = useLocalePreference();
    await changeLocale("en-US");

O hook aguarda a Server Action que persiste o cookie HttpOnly e chama router.refresh() em transição. A nova renderização por request reconcilia Server Components, Client Components e html.lang sem reload completo nem alteração do pathname. Desabilitar a UI durante isPending e manter feedback acessível se changeLocale retornar false. Evitar UI que atualize somente contexto cliente e deixe conteúdo RSC no idioma anterior. Não colocar bandeiras nesta task.

## 8. Formatação e contratos preservados

O locale está disponível por getLocale (server) e useLocale (client), preparando Task 25.8 para formatar datas, horas, números, percentuais e moedas sem converter valores ou inferir timezone. Esta etapa **não** altera cálculos do FinOps, Billing, Flow, Reservations, contratos HTTP/API, enums, ARNs, OCIDs, resource IDs ou nomes oficiais AWS/OCI.

## 9. Validação e limitações

Comandos previstos na raiz do frontend:

    npm ci
    npm run lint:i18n
    npm run typecheck
    npm test
    npm run lint:design-system
    npm run lint:brand
    npm run build

O teste específico cobre resolver e normalizar locales, cookie inseguro/inválido, duração e segurança de cookie, paridade, duplicação, ICU, pluralização real e as conexões SSR/provider/action. Os testes estáticos de Root Layout não substituem um navegador: hidratação real, refresh de RSC, cache intermediário e seis combinações de tema/idioma exigem smoke/e2e posterior na 25.3 e QA completo na 25.9.

**Atenção:** testes que apenas verificam fontes não comprovam ausência de hydration mismatch. A validação de CI deve ser registrada separadamente dos testes de navegador. A infraestrutura está preparada para Task 25.3 após typecheck/build e verificações CI bem-sucedidas; não antecipar tradução de telas nem modificar Topbar nesta PR.
