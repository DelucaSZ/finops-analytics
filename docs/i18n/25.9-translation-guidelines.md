# Aven — Diretrizes de internacionalização (Task 25.9)

**Produto:** Aven. **Locales oficiais:** `pt-BR` (padrão) e `en-US`. **Infraestrutura:** Next.js 15, React 19, `next-intl@4.3.5`. As regras são obrigatórias em funcionalidades futuras.

## 1. Arquitetura existente — não duplicar

- Catálogos: `frontend/i18n/messages/pt-BR.json` e `en-US.json`; JSON sem chaves duplicadas.
- Resolução SSR: `frontend/i18n/request.ts`, `server.ts` e `catalog.ts`; `LocaleProvider` no `app/layout.tsx`, `html lang={locale}`.
- Preferência: cookie HttpOnly `aven.locale`, validado e atualizado **somente** por `i18n/actions.ts`; `useLocalePreference` e controle na Topbar.
- Se locale não for reconhecido, usar `pt-BR`. Não criar localStorage, novas tabelas, provider paralelo ou prefixo `/[locale]`.

## 2. Textos e namespaces

Escolher namespace por responsabilidade de domínio, reaproveitando `common`, `shell`, `errors`, `auth`, `accessibility`, `dashboard`, `billing`, `flow`, `inventory`, `reservations`, `opportunities`, `settings`, `scans`, `collections`.

Textos genéricos intrínsecos a componentes compartilhados pertencem ao namespace do componente; labels específicos de domínio ficam com o consumidor. Traduzir imediatamente **ambos** os idiomas: nunca depender do fallback como forma normal de operar.

Client Components usam:

```tsx
const t = useTranslations("settings.https");
return <h2>{t("currentState")}</h2>;
```

Server Components podem obter um tradutor com `getTranslations` de `next-intl/server` dentro de um escopo de requisição, sem armazenamento global mutável.

```tsx
const t = await getTranslations("common");
return <span>{t("actions.save")}</span>;
```

A mesma chave relativa deve existir nos catálogos, com significado equivalente. Preferir `useLocale()` nos consumidores Client que precisem passar locale a helpers de apresentação.

## 3. ICU, parâmetros e pluralização

Usar placeholders nomeados consistentes. O validador compara assinatura ICU entre locales e exige `other`. Exemplo **existente** `common.results.count`:

```json
"count": "{count, plural, =0 {Nenhum resultado} one {# resultado} other {# resultados}}"
```

```json
"count": "{count, plural, =0 {No results} one {# result} other {# results}}"
```

Consumir via `t("results.count", {count})`. Parâmetros de interpolação e seletor plural não devem divergir. Para mensagens contextuais, ver `settings.https.validatedCertificate` com `{issuer}` e `{date}`. Não concatenar gramaticalmente fragmentos traduzidos quando uma única mensagem ICU expressar melhor a frase.

## 4. Erros, enums e conteúdo externo

- Traduzir labels de enums sem alterar códigos transportados na API, URLs, query params ou storage. Ex.: `endpointLabels[status.endpoint_validation.status]` em HTTPS é um mapa de apresentação, mantendo `VERIFIED`, `MISMATCH` etc.
- Preferir `error.code` estruturado para escolher chave local; não fazer `.replace("texto do backend", "...")` em mensagens livres.
- Mensagens livres de backend, terceiros e dados fornecidos pelo usuário não são traduzíveis sem contrato específico; documentar dependências e não esconder diagnóstico operacional indispensável.
- Credenciais, tokens, ARN, OCID, AWS Account IDs, SKUs, datas ISO, moedas e os códigos `NU` são dados técnicos, não tradução de copy.

## 5. Números, moeda e precisão

Usar `i18n/formatters.mjs`: `formatLocaleNumber(value,locale)`, `formatLocaleCurrency(value,currency,locale)`, `formatLocalePercentage(value,locale,{valueMode:"points"|"fraction"})`, `formatLocaleDate`, `formatLocaleDateTime`, `formatLocaleDuration` e `formatLocaleRelative`.

**Nunca converter moeda ou alterar valores financeiros por locale.** A moeda é o código real recebido do backend. Para strings decimais de preços, manter a string canônica e precisão; não converter para `Number` sem motivo.

`valueMode:"points"` indica `12.5 → 12,5%`; `valueMode:"fraction"` indica `0.125 → 12,5%`. Não inferir automaticamente a escala.

## 6. Datas, timezone e calendários

`YYYY-MM-DD` é data civil: `formatLocaleDate` mantém dia/mês/ano, sem deslocamentos de timezone. Timestamps são instantes: `formatLocaleDateTime` usa UTC determinístico por padrão, salvo timezone **de negócio explícito**. Locale não é timezone. Nunca alterar `end_date` exclusivo de Billing, filtros ISO, persistência ou `Date` de domínio por motivos de exibição.

`formatNu(value,locale)` no helper de RDS apresenta quantidade com separadores regionais e sufixo técnico `NU`. Não alterar required/covered/allocated/uncovered, cálculo nem porcentagem.

## 7. Acessibilidade e Design System

Localizar `aria-label`, `aria-description`, `aria-describedby` quando seu conteúdo for texto, placeholders, título, erro, tooltip, estados de interação e atributos de leitores de tela. Bandeira não substitui nome de idioma. Verificar foco/teclado do seletor e sincronização de `html lang` com SSR.

Todo ajuste visual deve utilizar tokens semânticos Aven; não criar dimensões rígidas para acomodar traduções. Testar texto longo nas combinações pt/en, light/dark/system e desktop/tablet/mobile.

## 8. Testes e quality gates

```bash
cd frontend
npm ci
npm run lint:i18n
npm run lint:i18n:references
npm run lint:i18n:coverage -- --report
npm run lint:i18n:coverage -- --base <BASE_COMMIT_SHA>
npm run typecheck
npm test
npm run lint:design-system
npm run lint:brand
npm run check:visual-regression
npm run build
```

- `check-i18n.mjs`: paridade, duplicidade, ICU, placeholders, valores vazios e namespaces.
- `check-i18n-references.mjs`: identifica chaves estáticas ausentes, relata pontos dinâmicos e possíveis órfãs. Não exclui chaves automaticamente.
- `check-i18n-coverage.mjs`: analisador AST de JSX, atributos e objetos de apresentação. Em `--report`, apenas inventaria; em `--base`, falha se novos candidatos de copy aparecerem sem tradução. Não trata todo código como copy.
- `scripts/i18n-coverage-exceptions.json`: exceções incrementais por fingerprint `[file,kind,text]` e justificativa de pelo menos 20 caracteres. Exceções técnicas exigem revisão.
- `tests/aven-i18n-final-qa.test.mjs` e testes 25.2–25.8: regressão de tradução, contratos e apresentação.
- CI usa SHA-base do PR; **não** trata scanner estático como homologação funcional/visual.

## 9. Checklist de PR

Cada nova rota/componente deve incluir copy pt-BR/en-US, interpolação/ICU, labels acessíveis, apresentação de valores, fallback e testes de invariância do contrato. Revisar todos os estados realmente suportados (loading/empty/error/partial/success/interactions) e a experiência no navegador. A aprovação depende de evidências reais, não apenas de um catálogo preenchido.

## Padrões verificados na Task 25.9

- Textos de páginas financeiras, como `app/settings/usage-costs/page.tsx`, devem usar `useTranslations("settings.usageCosts")`; nunca traduzir os valores `group_by`, `cloud_account_id`, enums e `pricing_unit` enviados à API.
- Mensagens genéricas de erro compartilhadas em `lib/api.ts` têm traduções em `errors.api`; mensagens livres do servidor permanecem conteúdo externo e devem migrar para código estruturado quando se exigir localização confiável.
- `StatusBadge` usa `common.status` somente no texto apresentado; `data-status` e status persistido continuam invariantes.
- `ThemeSelector` mantém opções `light`, `dark` e `system` inalteradas enquanto `settings.appearance` traduz seus labels e descrições.
- O smoke browser seguro `npm run smoke:i18n:browser` usa Chromium, proxy HTTPS local efêmero e fixture não destrutiva para `/auth/me`. Ele roda no CI após o build; exige Chromium e `playwright-core` instalados no runner. Screenshots e console de hydration são evidências parciais, não homologação de todas as rotas.
