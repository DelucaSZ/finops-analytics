# Task 25.1 — Translation Key Architecture (proposta para 25.2)

**Aven — FinOps Analytics** · Base auditada: `main` @ `52c8a739e38d71becb243873c0cee9277acd70a0` · 2026-11-06

> Documento de **decisão/proposta**. Nenhum catálogo, provider, seletor, rota, dependency ou componente foi criado nesta task.

## 1. Contrato de locale

| Dimensão | Decisão proposta |
| --- | --- |
| Locales aceitos | `pt-BR`, `en-US` (identificadores canônicos, sem alias automático) |
| Padrão | `pt-BR`, inclusive quando não houver cookie; não autoselecionar idioma do navegador |
| Fonte de verdade | cookie server-readable de preferência, sugestão `aven.locale` |
| URLs | manter exatamente `/billing`, `/inventory`, `/settings` e demais rotas existentes |
| Biblioteca | `next-intl`, **sem locale routing**; usar `getRequestConfig` para escolher locale a partir do cookie |
| Componentes cliente | `NextIntlClientProvider` com locale/messages que já foram renderizados no servidor |
| Componentes servidor | utilitários `getTranslations`, `getLocale` e `generateMetadata` por request, onde necessário |
| Atualização | seletor altera cookie via endpoint/server action da aplicação, atualiza provider/árvore via `router.refresh()` sem recarregar path |
| Fallback de locale | valores ausentes/fora da whitelist => `pt-BR` de forma determinística |
| Persistência | `Path=/`, `SameSite=Lax`, `Max-Age` durável, `Secure` se HTTPS; `HttpOnly` somente se escrita por server action/route handler |
| Histórico | não depender só de `localStorage`: o servidor não o enxerga no SSR |
| Compatibilidade | preservar `ThemeProvider`, bootstrap de tema, layout, sessão, token design e URLs |

**Por que não usar `localePrefix:'never'` automaticamente?** Essa opção de roteamento do `next-intl` requer a árvore `[locale]` para reescritas internas. Para o Aven, o exemplo oficial **sem roteamento por idioma** preserva melhor as rotas App Router existentes e evita mover 33 páginas apenas para localizar o conteúdo. Reavaliar somente se houver requisito futuro de URLs publicamente indexadas por idioma.

### Contrato de SSR/hidratação (obrigatório na 25.2)

1. O servidor lê o cookie, valida a whitelist e carrega apenas o catálogo escolhido; não consulta `window` ou `localStorage`.
2. O Root Layout renderiza `<html lang=...>` segundo o **mesmo** locale. Não usar `suppressHydrationWarning` como compensação de divergência de texto.
3. O provider recebe um snapshot determinístico de locale e mensagens usados no SSR. Todo componente cliente que renderiza texto deve ler deste contexto.
4. A atualização dispara uma nova renderização de servidor coerente com o cookie e não muda URL. Garantir que caches de RSC/edge não sirvam HTML ou tradução de outro locale.
5. A preferência inválida é normalizada para `pt-BR`, sem gerar loop de refresh ou cookie inválido.
6. `ThemeProvider` continua independente. O provider i18n fica acima da árvore de `ThemeProvider → AvenAmbientBackground → ToastProvider → AppShell`, para cobrir Shell, feedback e páginas.
7. A metadata localizada deve ser produzida no lado servidor; o nome próprio *Aven* permanece igual.

**Observação:** projeto utiliza Next.js 15 (não portar exemplos exclusivos de `proxy.ts` do Next 16 sem adaptar a `middleware.ts` se middleware for usado). Preferir inicialmente nenhum middleware de i18n.

**Preferir conceito ao texto:** duas telas podem mostrar "Ativo", mas status de recurso e status de sessão podem ter traduções contextuais distintas. Compartilhar em `common` somente ações com semântica idêntica. Evitar chave `label1`, `text42`, `buttonPortuguese`. Não usar hashes/linhas como chaves definitivas; o CSV contém **sugestões de varredura** que exigem curadoria antes de virarem catálogos.

### Nomes das chaves

- Namespace `lowercase`; segmentos `camelCase` e semanticamente tipados: `billing.period.custom`, `settings.sessions.lastActivity`.
- Preferir `.title`, `.description`, `.label`, `.placeholder`, `.tooltip`, `.ariaLabel`, `.empty`, `.error` para a função da string.
- Estado de domínio: `opportunities.status.rejected`, não `common.rejected` por padrão.
- Não criar chaves diferentes para duas instâncias do **mesmo** shared component; traduções no nível do dono do texto.
- Não colocar valores de runtime (IDs, ARN, OCID, nome de conta, moeda) dentro da chave; usar parâmetros.
- Chaves são contratos estáveis entre `pt-BR` e `en-US`: renomear com migração atômica de ambos os catálogos e testes.

## 3. Interpolação e plurais

- Usar **parâmetros nomeados**, nunca concatenar texto ao lado de números/datas/nomes técnicos para formar frase traduzível.
- Valores de runtime entram como argumentos separados, ex.: `t('inventory.resources.count', {count})`.
- Exemplos ICU, para ambos os catálogos:

```json
{
  "inventory": {
    "resources": {
      "count": "{count, plural, =0 {Nenhum recurso} one {# recurso} other {# recursos}}"
    }
  }
}
```

O texto em inglês deve usar sua gramática própria, não ser uma substituição palavra a palavra. Evitar plural montado em `count === 1 ? ...` quando a frase tiver ordem variável.

- Quando o parâmetro não for seguro para markup, apresentar como texto escapado.
- Para link ou ênfase dentro de tradução, usar rich text com tags explicitamente aceitas, nunca `dangerouslySetInnerHTML` com mensagem externa.
- Não interpolar partes de sintaxe de cloud IDs ou unidades de domínio na string do catálogo. Exibir como componentes/valores com formatação apropriada.
- Mensagens de data: passar objetos `Date` ou valores canônicos para formatadores; não passar strings já pré-localizadas.

## 4. Validações e erros dinâmicos

### Camada de interface

```text
errors.http.unauthorized
errors.http.forbidden
errors.http.notFound
errors.http.unprocessable
errors.http.tooManyRequests
errors.http.internal
errors.network.timeout
errors.auth.sessionExpired
errors.auth.invalidCredentials
errors.rdsCoverageNotCalculated
```

Os erros de API devem seguir esta prioridade futura:

1. Para `{code, parameters}` reconhecido, resolver chave local por tabela de códigos, interpolando parâmetros aprovados.
2. Para `detail` legado reconhecido pela camada atual de compatibilidade, mapear **exatamente** essa string para uma chave estável (transição), sem remover campos `status`/`detail`/`code` de `ApiError`.
3. Para código HTTP sem mapeamento, usar fallback localizado por status.
4. Para mensagem externa inesperada, usar fallback localizado para usuário e preservar detalhe técnico de forma segura para diagnóstico/log, sem tratá-lo como tradução confiável.

**Evidência:** `frontend/lib/api.ts:67-107` atualmente mapeia alguns detalhes em inglês para texto português e, em outros casos, expõe `detailText` do backend. `backend/app/api/routes/rds_reservations_dashboard.py:43-48` já usa `code + message`; outras rotas retornam texto livre em inglês/português.

**Não** mudar API, schema ou backend na Task 25.1. Se um contrato precisar de novos códigos, registrar em decisão posterior específica, com versão e compatibilidade retroativa.

Validações de formulários devem usar chaves como `auth.validation.required` com parâmetros `fieldName`; não montar string "Campo " + nome. Códigos de validação internos, payloads e identificadores não são traduzidos.

## 5. O que traduzir e o que preservar

| Tipo | Regra |
| --- | --- |
| UI, placeholders, ARIA, tooltips, empty/loading/error/confirmation | Traduzir, com testes de acessibilidade e layout |
| Nome próprio *Aven*, nomes AWS/OCI/RDS, códigos oficiais dos serviços | Preservar |
| AWS ARN, OCI OCID, resource ID, account ID, region code, enum técnico, chave de API/storage | Preservar byte a byte |
| `amount`, `currency`, `percent`, valor de métricas, unidades de reserva | Preservar **valor**, formatar representação pela Task 25.8 |
| Nome/tag/descrição fornecidos pelo usuário | Não traduzir conteúdo |
| Mensagem controlada pelo Aven via código estável | Traduzir o *significado* do código na UI |
| `detail` de serviço externo | Não traduzir cegamente; usar fallback e diagnóstico protegido |

Nenhum componente deverá alterar arredondamento, moeda original, sinal, precisão ou operações sobre dados quando o idioma mudar.

## 6. Formatação regional

Criar na 25.8 uma camada central (ou wrappers orientados pelo locale do provider) para:

- `formatCurrency(amount, currency, locale)`: `Intl.NumberFormat(locale, {style:'currency', currency})`; **não efetuar conversão de USD para BRL**.
- `formatNumber` e `formatPercent`: locale da UI, arredondamento dependente da regra financeira preexistente.
- `formatDateTime(instant, locale, timezone)`: distinguir data civil (`YYYY-MM-DD`) de instante UTC com offset. Definir timezone pela regra do dado/conta/usuário, **nunca** deduzir fuso apenas de `pt-BR`.
- `formatRelativeTime`: pluralização/locale corretos com `Intl.RelativeTimeFormat` e valores absolutos para auditoria.
- `formatRange`: início/fim inclusivo conforme contratos de Billing (não introduzir off-by-one) e labels traduzidos.
- Unidades técnicas e percentuais: sinal e escalas são invariantes; traduzir apenas rótulos/representação quando apropriado.

Pontos de atenção no código atual: `frontend/lib/api.ts:113-126` fixa `pt-BR`; `frontend/components/aven/displays.tsx:36,74,124` assume `en-US`; páginas e helpers fazem formatação local por conta própria. O CSV distingue formatação de tradução literal.

## 7. Acessibilidade, seletor e responsividade

- Controle de idiomas deve ficar ao lado de `ThemeControl` na Topbar; usar bandeiras BR/EUA como pista **visual**, nunca como único nome acessível.
- Exibir nome do idioma no popover, indicação do selecionado (`aria-current` ou `aria-checked` conforme papel adotado), suporte a teclado, foco, Escape e tooltip.
- Rótulos acessíveis: "Idioma: Português (Brasil)" / "Language: English (United States)"; não inferir idioma a partir de bandeira.
- Definir `<html lang>` por SSR. Traduzir `aria-label`, `aria-description`, leitor de tela, `title`, metadata.
- Revalidar Topbar desktop/mobile, Sidebar expandida/recolhida, filtros, tabelas densas, dialogs e charts com frases longas em ambos os idiomas.
- Respeitar Design Tokens e Theme Engine Aven. Nenhuma cor, espaçamento, radius ou tipografia hardcoded em novas implementações.
- Para identificadores extensos, manter truncamento visual, `title` completo e valor copiado sem transformação (ex.: OCID).

## 9. Revisão do Translation Inventory

`25.1-translation-inventory.csv` contém caminho real/linha, texto observado, idioma inferido, categoria, prioridade, task, chave **provisória**, indicação de interpolação e `review_status`.

1. Começar pelos registros `candidate_verified_by_source`, verificar contexto de página e aceitar chaves semânticas.
2. Revisar `requires_review` comparando source, componente consumidor, runtime e contratos. **Não** importar automaticamente todas as chaves propostas.
3. Migrar shared component uma vez; consumidores passam texto/prop ou chave contextual conforme domínio.
4. Ao finalizar cada task, medir cobertura de tradução **efetivamente renderizada** e eliminar mapeamentos baseados em strings do backend.
5. Ao terminar 25.9, garantir paridade de catálogos e testes transversais.

O audit inventaria ocorrências; não cria tradução definitiva nem mede porcentagem de tradução completada.
